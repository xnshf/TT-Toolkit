# 版本对照表（本地 / 云端）

用途：记录每个**已发布版本**对应的提交与数据结构影响，用来判断「什么时候需要考虑兼容、什么时候不需要」。
每次推送后只需更新下面「当前状态」里的一格。

## 名词

- **commit hash（提交哈希）**：每个提交的 SHA-1 值，日常简称 **commit SHA** 或**提交 ID**。
- **short hash（缩写提交哈希 / 短哈希）**：Git 默认显示的前 7 位缩写形式，只保证在当前仓库内唯一即可。
  需要更长时用 `git rev-parse --short=12 <ref>`。

## 何时需要考虑兼容

判断顺序：

1. **只对已发布过的版本负责。** 未发布的版本之间怎么改都不需要兼容处理——`0.8.0` 开发过程中主题 id 换过三轮（`obsidian`/`forest`/`daylight` → `daisyUI` 套装 → 加回 `parchment`），因为从未发布过旧形态，所以不需要迁移代码。
2. **`schemaVersion` 变化 ⇒ 必须写迁移**，并在文档与测试中同步。目前仍是 `1`，从未变过。
3. **新增字段 + 缺省补齐 ⇒ 向后兼容，不需要迁移。** `entryMode`（0.7.2）与 `theme`（0.8.0）都是这一类：旧数据没有该键时补安全默认，读旧数据不会失败。
4. **删除或重命名已发布的枚举取值 ⇒ 需要迁移或显式回退。** 例如主题 id。
   `0.8.0` 起未知取值会回退到安全默认并记 `warn`、在设置页给出提示，因此不会再出现「读到一个旧枚举值就整个工具箱打不开」。
5. **删除已发布的存储键 ⇒ 需要迁移或保留。** 目前被下架功能的键都保留未删。
6. **纯样式、纯文案、纯性能改动 ⇒ 不需要兼容处理。**

反向使用：如果某个改动**没有**落在第 2 / 4 / 5 类，就不必写迁移、不必加 `schemaVersion`、也不必为旧数据写兼容分支。

## 维护步骤

1. 推送后，把「当前状态」表里**云端**一行更新为新的版本与短哈希。
2. 若本次改动落在上面第 2 / 4 / 5 类，在「版本对照」表新增一行并在「数据结构影响」里写明。
3. 若只是样式或文案，只更新云端一行即可——这正是这张表省事的地方。
